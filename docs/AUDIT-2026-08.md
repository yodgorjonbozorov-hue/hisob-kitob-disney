## 3. KOD SIFATI

### 3.1. Takroriy kod (eng katta muammo)

**Modal + forma patterni 6+ marta takrorlangan.** Har birida bir xil:
```tsx
const [error, setError] = useState<string | null>(null);
const [loading, setLoading] = useState(false);
async function submit(e: FormEvent) {
  e.preventDefault(); setLoading(true); setError(null);
  const res = await fetch(...); const data = await res.json();
  if (!res.ok) { setError(data.error); setLoading(false); return; }
  onDone();
}
```
**Yechim:** `useApiForm()` hook yozing yoki `react-hook-form` + `zod` resolver qo'shing. ~400 satr yo'qoladi.

**API route boilerplate takrorlanadi:**
```ts
const businessId = await resolveActiveBusinessId(user);
if (!businessId) return NextResponse.json({ error: "Biznes topilmadi" }, { status: 404 });
const body = await request.json();
const parsed = schema.safeParse(body);
if (!parsed.success) return NextResponse.json({ error: ... }, { status: 400 });
```
20+ route'da. `withBusiness(schema, handler)` wrapper yozing.

**Narx formatlash / parse** har modal'da qayta yozilgan (`NarxInput`, `formatSom`, `parseInt(x.replace(...))`).

### 3.2. Noto'g'ri React ishlatilishi

- **`Button` da `type` yo'q** → forma ichida default `submit`. Bu klassik xato manbai. `type="button"` default qiling.
- **`useEffect(() => setProducts(initialProducts), [initialProducts])`** (`OmborClient.tsx:27`) — server props'ni state'ga ko'chirish antipattern. `key` prop yoki to'g'ridan-to'g'ri prop ishlating.
- **`React.memo` 0 ta.** 46 `useState` bo'lgan komponentda har bosishda butun daraxt qayta render bo'ladi.
- **`useMemo`/`useCallback` faqat 17 ta** — 50 client komponentga juda kam.
- **50 ta `"use client"`** — ko'pi kerak emas. `TransactionList`, `ReceiptList` kabi ro'yxatlar server komponent bo'lishi mumkin edi.

### 3.3. Noto'g'ri Next.js ishlatilishi

- 🔴 **`loading.tsx` — 26 sahifada 0 ta.** Streaming/Suspense umuman ishlatilmagan. Har navigatsiya barcha DB so'rovlari tugaguncha oq ekran. `Skeleton.tsx` komponenti bor, lekin hech qayerda `loading.tsx` sifatida ishlatilmagan. **Bu eng oson tuzatiladigan katta UX yutuq.**
- 🔴 **Kesh yo'q:** `unstable_cache`, `revalidate`, `revalidateTag`, `revalidatePath` — hech biri ishlatilmagan. O'rniga 47 ta `router.refresh()` (butun sahifani serverdan qayta so'rash).
- **`error.tsx` faqat 2 ta** — har modul uchun kerak.
- **`searchParams` validatsiyasiz** ishlatiladi: `parseInt(searchParams.page)` → `NaN` bo'lishi mumkin.

### 3.4. Prisma xatolari

- 🔴 **`ensureCategory` race condition** (`services/inventory.ts:35`): `findFirst` → `create`. Ikkita parallel sotuv → `@@unique([nomi,turi,businessId])` buziladi → **500 xato**. `upsert` ishlating.
- 🔴 **53 ta `findMany` `take` limitisiz.** `listProducts`, `getProductProfitability`, `listDebts`, `getDailyDynamics` — hammasini RAM'ga yuklaydi. 10 000 sotuvli biznesda serverni yiqitadi.
- **Tenant extension har unique amalda qo'shimcha so'rov qiladi** (`tenantDb.ts:104`). Bu xavfsizlik uchun to'g'ri, lekin har `update` = 2 so'rov, har `create` = 2 so'rov. Turso'da (~160 ms/so'rov, README'da o'zingiz yozgansiz) bu jiddiy.
- **`tenantClient` keshi cheksiz `Map`** — tenant soni oshgani sari xotira o'sadi. LRU qo'ying.

### 3.5. TypeScript

Umuman yaxshi (`strict: true`, `any` deyarli yo'q). Lekin:
- `data: {...} as never` — Prisma tipini majburan sindirish (`billing/payme.ts:96`, `click.ts:88`, `provider.ts:41`). Bu tenant extension tipi bilan kelishmovchilikni yashirmoqda — to'g'ri tiplash kerak.
- `search/route.ts` da `as { id: string; ... }[]` — natijani qo'lda kast qilish. Prisma tipini ishlating.
- Rol `String` sifatida saqlanadi (SQLite enum yo'q) — bu tushunarli, lekin DB darajasida `CHECK` constraint yo'q.

### 4.1. Normalizatsiya — asosan yaxshi

### 4.2. 🔴 KRITIK: Cascade / referensial yaxlitlik yo'q

```
$ grep -c "onDelete" prisma/schema.prisma
0
```

**Butun sxemada birorta `onDelete` yo'q.** Bu degani:
- Biznesni o'chirib bo'lmaydi (FK cheklovi) — lekin bu tekshirilmagan, xato foydalanuvchiga 500 bo'lib chiqadi.

- `Task.dealId`, `Debt.productId`, `Deal.contactId` — o'chirilganda nima bo'ladi? Aniqlanmagan.

**Har relatsiyaga aniq `onDelete` yozing:** `Cascade` (bola yozuvlar), `Restrict` (moliyaviy), `SetNull` (ixtiyoriy bog'lanish).

### 4.3. 🔴 Indekslar yetarli emas

`Transaction` da bitta-bitta ustun indekslari bor, lekin **kompozit indeks yo'q**. Barcha so'rovlar `businessId + sana` bo'yicha filtrlaydi:

```prisma
// HOZIR:
@@index([sana]) @@index([turi]) @@index([categoryId]) @@index([businessId]) @@index([userId]) @@index([deletedAt])

// KERAK:
@@index([businessId, deletedAt, sana])
@@index([businessId, turi, sana])
@@index([businessId, categoryId, sana])
@@index([businessId, userId, sana])
```
SQLite bitta so'rovda bitta indeks ishlatadi — hozirgi 6 ta alohida indeks deyarli foydasiz va yozishni sekinlashtiradi.

Shuningdek yetishmayapti: `Sale(businessId, createdAt)`, `Debt(businessId, isYopilgan, turi)`, `AuditLog(businessId, createdAt)`, `Payment(externalId)` — **`@unique` bo'lishi kerak** (hozir oddiy index, ikkita bir xil provider tranzaksiyasi yozilishi mumkin).

### 4.4. 🔴 Tranzaksiyalar yetishmayapti

`$transaction` faqat 4 joyda: `signup`, `subscribe`, `products/bulk`, `superadmin`.

## 5. XAVFSIZLIK AUDITI

### 🟢 Yaxshi qilingan
- **Tenant izolyatsiyasi** — `tenantDb.ts` da IDOR himoyasi (`UNIQUE_OPS` da yozuv egaligi tekshiriladi), `create`'da `businessId` tenantga tegishliligi tasdiqlanadi. **Bu darajadagi himoyani ko'p SaaS'da ko'rmaganman.**
- **Superadmin roli har so'rovda bazadan qayta tekshiriladi** (`superadmin.ts:14`) — sessiyaga ishonilmaydi. To'g'ri.
- Parol `bcryptjs` (10 rounds), `iron-session` (`httpOnly`, `secure`, `sameSite: lax`).
- Zod validatsiya barcha yozish route'larida.
- `createUserSchema` da `SUPERADMIN` yo'q — **privilegiya oshirish yo'li yopilgan**. To'g'ri qaror.
- Login javoblari umumiy ("Login yoki parol noto'g'ri") — foydalanuvchi sanashdan himoya.

### 🔴 KRITIK

**S-1. `CRON_SECRET` / `TELEGRAM_WEBHOOK_SECRET` fail-open**
```ts
if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) return 401;
```
`CRON_SECRET` sozlanmagan bo'lsa — `"Bearer undefined"` yuborgan har kim cron'ni ishga tushiradi: zaxira olinadi, statuslar o'zgaradi, barcha mijozlarga Telegram xabar ketadi. Webhook'da ham `secretToken: undefined` → grammy tekshiruvni butunlay o'tkazib yuboradi.
**Tuzatish:** ilova start'ida majburiy env tekshiruvi; secret yo'q bo'lsa route 503 qaytarsin.

**S-2. Zaxira — shifrlanmagan, parol hash'lari bilan, Telegram'da**
`lib/backup/send.ts` butun bazani (barcha tenantlar, barcha `parolHash`, telefon raqamlar, mijoz ismlari, moliyaviy raqamlar) gzip qilib **shifrlamasdan** Telegram kanaliga yuboradi.
- Telegram — uchinchi tomon, kanal kompromis bo'lsa hamma mijoz ma'lumoti oshkor.
- GDPR/PDPL nuqtai nazaridan — jiddiy buzilish.
- Enterprise mijoz buni ko'rsa shartnoma imzolamaydi.

**Tuzatish:** AES-256-GCM bilan shifrlang (kalit env'da), yoki S3/R2 + server-side encryption'ga o'ting. Parol hash'larini zaxiradan chiqarib tashlash mumkin emas (tiklash kerak), shuning uchun shifrlash **shart**.

**S-3. Rate limit serverless'da samarasiz**
`lib/rateLimit.ts` — `Map` xotirada. Vercel'da har lambda instansiyasi alohida. Hujumchi parallel so'rov yuborsa har biri yangi instansiyaga tushadi → **brute-force amalda cheklanmagan**.
**Tuzatish:** Upstash Redis yoki Turso jadval + atomik `UPDATE ... WHERE count < limit`.

### 🟠 YUQORI

**S-4. CSRF token yo'q.** `sameSite: lax` asosiy himoya beradi, lekin bu yagona qatlam. Eski brauzerlar va subdomain hujumlarida yetarli emas. Origin header tekshiruvi yoki double-submit token qo'shing.

**S-5. Payme/Click imzo taqqoslash timing-safe emas**
```ts
return login === "Paycom" && parol === key;        // payme.ts:213
if (req.sign_string !== clickSign(...))            // click.ts:191
```
`crypto.timingSafeEqual` ishlating. Shuningdek Payme/Click IP allowlist yo'q.

**S-6. Payme 12-soatlik timeout qoidasi amalga oshirilmagan.** Payme protokoli `CreateTransaction`dan 12 soat o'tgan tranzaksiyani bekor qilishni talab qiladi (`-31008`). Kodda yo'q → **Payme sandbox testidan o'tmaydi**.

**S-7. AI suhbat tarixi mijozdan keladi**
`/api/ai/chat` da `tarix` massivini foydalanuvchi to'liq boshqaradi — soxta `assistant` xabari yuborib model'ni chalg'itish mumkin. Tool'lar tenant-scoped bo'lgani uchun ma'lumot sizmaydi, lekin model xohlagan matnni chiqarishi mumkin. Tarixni serverda saqlang.

**S-8. `/api/search` cheklanmagan**
`contains` bo'yicha 4 jadvalda indekssiz qidiruv, rate limit yo'q, minimal 2 belgi. 1M yozuvli bazada bir necha parallel so'rov — DoS.

**S-9. ADMIN = OWNER (granular ruxsat yo'q)**
`isManager()` ikkalasini teng ko'radi. ADMIN OWNER'ning parolini almashtira oladi (`updateUserSchema` da `parol` bor) va uni o'chira oladi. Kompaniya egasi o'z dasturidan chiqib qolishi mumkin.

### 🟡 O'RTA
- **2FA yo'q**, sessiya bekor qilish (revoke) yo'q, parol tiklash oqimi yo'q (faqat superadmin qo'lda).
- **Xavfsizlik header'lari yo'q**: CSP, HSTS, X-Frame-Options, Referrer-Policy — `next.config.mjs` da `headers()` yo'q.
- **Telegram bog'lash kodi `Math.random()`** bilan — kriptografik emas. 6 raqamli kod, 10 daqiqa TTL, urinishlar cheklanmagan → **brute-force bilan boshqa hisobga ulanish mumkin** (10 daqiqada 1M kombinatsiya realistik emas, lekin rate limit qo'ying va `crypto.randomInt` ishlating).
- SQL Injection: **topilmadi** ✅ (Prisma + bitta `$queryRaw` parametrlangan).

4. **Buxgalterlar dasturi:** buxgalter 5 mijoz olib kelsa — komissiya
5. **Trialni 14 → 21 kunga** (biznes bir oylik siklni ko'rishi kerak)

**Siz yaxshi dasturchisiz.** Tenant izolyatsiyasi qatlami, modul registry, dizayn tokenlari — bular tajribali arxitektor ishi. Izohlar sifatli, `any` deyarli yo'q, testlar bor, hujjatlar bor. Bu O'zbekistondagi ko'p loyihadan yuqori.

**Lekin siz ERP yozmadingiz.** Siz juda yaxshi kirim-chiqim dasturini yozdingiz va unga ombor, CRM va bot qo'shdingiz. "ERP" so'zini ishlatish uchun xarid, ishlab chiqarish, kadrlar, aktivlar, hujjat aylanishi va tasdiqlash oqimi kerak. Hozir bularning bittasi ham yo'q.
